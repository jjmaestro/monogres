# `monoext` in ~30 lines

This directory is the minimum working consumer of `monoext`. Read this
if you want to understand what a downstream Bazel project gets by calling
`monoext.monogres(...)`, and what to `load(...)` from the generated
hubs.

## 1. `MODULE.bazel` declaration

A downstream module declares `monoext.monogres(...)` once:

```starlark
bazel_dep(name = "monogres")  # (+ local_path_override or registry)

monoext = use_extension("@monogres//monoext:monoext.bzl", "monoext")
monoext.monogres(
    name = "pg",
    base = "@monogres//catalog/postgres:repo.json",
    extensions = "@monogres//catalog/extensions:index.json",  # optional
)
use_repo(monoext, "pg", "pg_ext", "pg_pkgs")
```

`name = "pg"` becomes the hub prefix: the extension creates three external
repos from this single tag.

## 2. The three hubs `use_repo` brings in

| Repo         | What it is                                            |
|--------------|-------------------------------------------------------|
| `@pg`        | PostgreSQL builds, one per (version × option-set)     |
| `@pg_ext`    | External extensions (citus, sslutils, …) + PG contrib |
| `@pg_pkgs`   | Debian packages resolved for all PG + extension deps  |

Each is a hub repo generated by monoext's repo rules. Their file trees and
`all.bzl` / `repo.bzl` contents are the public API.

## 3. Where the data lives

- `@pg//:all.bzl` exports `CFG`, `VERSIONS`, `OPTION_SETS`, `DEFAULT_VERSION`.
  `CFG.default` is the recommended (version, option_set) pair.
- `@pg//:introspect.bzl` exports `INTROSPECTIONS`: a
  `{(version, option_set): alias_name}` map for static introspect data.
- `@pg_ext//:all.bzl` exports `CFGS`, `EXTENSIONS`, `REPOS` (externals) plus
  `CFGS_CONTRIB`, `CONTRIB_EXTENSIONS`, `REPOS_CONTRIB` (contribs).
- `@pg_ext//<ext>:repo.bzl` re-exports per-extension `DEFAULT_VERSION`, `LOCK`,
  `METADATA`, `REPO_NAME`, `VERSIONS`.
- `@pg_pkgs//deb/<pkg>:<pkg>` is the cross-arch alias for a resolved Debian
  package; `@pg_pkgs//deb/<pkg>/<arch>:<arch>` is the per-arch pin.

### Target deps on both hubs

Each target in `CFG.targets` (base) and `CFGS[ext][i].targets[j]` (ext) carries
a symmetric `deps` struct:

```starlark
target.deps = struct(
    buildtime = struct(
        sysroot  = "@pg//18.1/deps/buildtime:sysroot",           # or None
        packages = ["@pg//18.1/deps/buildtime/pkgs:libssl-dev",  # or []
                    ...],
    ),
    runtime = struct(
        sysroot  = "@pg//18.1/deps/runtime:sysroot",
        packages = ["@pg//18.1/deps/runtime/pkgs:libssl3", ...],
    ),
)
```

Use `deps.<kind>.sysroot` to link against the flattened deb tree (90% case).
Use `deps.<kind>.packages` when you need specific package labels (e.g. to
package a subset for a Docker image). Contrib extensions don't carry a `deps`
field — they inherit PG's deps transitively since they're built inside PG.

## 4. The example itself

[`BUILD.bazel`](./BUILD.bazel) is a single `build_test` that names one target
from each of the three hubs:

```sh
bazel test //public/consumer
```

The `build_test` forces Bazel to resolve and build each target, exercising the
full hub-generation pipeline end-to-end. No extra glue rule is needed; the
hub labels themselves are the public API.

## 5. Going further

Once you have this building, the next steps depend on your use case:

- **Build a specific extension**: `bazel build @pg_ext//<ext>:<ext>`, resolves
  to the ext's default PG version target.
- **Pin a specific (ext, PG) pair**: `bazel build
  @pg_ext//<ext>/<ext_v>/<base_v>:<base_v>`.
- **Consume an extension's source dir**: `@pg_ext//<ext>:dir`, useful when
  integrating a build rule that wants source access.
- **Depend on an extension's sysroot**: buildtime or runtime debs
  `@pg_ext//<ext>/<ext_v>/deps/{buildtime,runtime}:sysroot`.

The `examples/private/` tree in this same workspace contains internal e2e tests
that exercise every public API surface; look there for exhaustive usage
patterns.
